# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A macOS menu-bar agent (`LSUIElement`, no Dock icon) that translates the current selection on **double Cmd+C** using a local LLM (Gemma via Ollama on `localhost:11434`) and streams the result into a floating panel near the cursor. Two empirical decisions are load-bearing and must not be changed lightly: `think:false` is mandatory (Gemma 4 otherwise burns 10–26s on reasoning tokens for an identical translation), and the native REST `/api/generate` is used over the OpenAI-compatible `/v1` layer (which doesn't expose `keep_alive`).

The sibling docs each own something this file doesn't: `README.md` is the user-facing install/usage text, `PRODUCT.md` + `DESIGN.md` are the landing page's brand contract (Polish, with the indigo/coral tokens and type scale — change the landing only through them), GitHub issues track planned work and `docs/DISTRIBUTION.md` the release/signing details.

## Build & test

The Xcode project is **generated** by XcodeGen and is git-ignored. Never edit `*.xcodeproj` by hand — change `project.yml`, then regenerate. All four scripts regenerate the project first, so new source files are picked up automatically.

```bash
scripts/gen.sh      # regenerate Glosso.xcodeproj from project.yml
scripts/build.sh    # xcodegen generate + xcodebuild (Debug, arm64) → .build/dd/...
scripts/run.sh      # build + open the app (look for the bubble icon in the menu bar)
scripts/test.sh     # xcodebuild test → .build/TestResults.xcresult
scripts/package.sh  # Release build + signature-preserving zip → .build/release/Glosso.zip
```

`scripts/package.sh` produces a standalone `.zip` for a personal install: unzip, drag `Glosso.app` to `/Applications` (it then shows in Launchpad/Spotlight and runs without Xcode). It uses `ditto` (not `zip`) so the signature survives. Signed with the stable self-signed `Glosso Self-Signed` identity, **not notarized** (no Apple Developer account): first launch on another Mac needs a one-time right-click → **Open**. The "Launch at login" toggle (`SMAppService.mainApp`) only registers reliably once the app lives in `/Applications`.

**Builds and `xcodebuild` must run outside the sandbox** (`dangerouslyDisableSandbox: true`). Inside the sandbox they fail with `Operation not permitted`. `gh` and other network calls (GitHub API, Ollama over TLS) also need `dangerouslyDisableSandbox: true` — in the sandbox they fail with a TLS cert error (`OSStatus -26276`), not the build's `Operation not permitted`. During `/babysit-pr`, resolving a `claude-review` thread (`gh api graphql … resolveReviewThread`) is user-authorized in two cases: (1) findings actually fixed in committed code, and (2) findings you deliberately skipped after posting a rationale reply on the thread (low-value, or whose only fix would change a documented design decision). Leave a thread **unresolved only** when it is genuinely handed to a human — an un-adjudicable product/design call you did not decide yourself. The Bash tool's shell is **zsh** — unquoted `$var` is not word-split; iterate lists with `while IFS= read -r` (a `for x in $list` runs once on the whole string).

Signing uses a **stable self-signed certificate** (`Glosso Self-Signed`, `CODE_SIGN_STYLE: Manual`, no `DEVELOPMENT_TEAM` — created once in Keychain as Code Signing / Always Trust). It is deliberately constant because the Accessibility (TCC) grant is pinned to the signing identity: reusing the same cert keeps the grant across updates (verified A→B), whereas an ad-hoc signature would reset it on every release. Hardened runtime is **Release-only** — Debug sets `ENABLE_HARDENED_RUNTIME: NO` and `ENABLE_DEBUG_DYLIB: NO`, otherwise library validation rejects the self-signed (no-Team-ID) unit-test bundle and `scripts/test.sh` crashes at bootstrap with "different Team IDs". `CFBundleShortVersionString` is bound to `$(MARKETING_VERSION)`. Switching the signing identity needs a one-time re-grant (`tccutil reset Accessibility com.mirek.glosso`, then re-add the app). A **Keychain password prompt during `scripts/run.sh` is the signing step, not the app** — `codesign` fetches the `Glosso Self-Signed` private key, and its dialog reads like the app asking for a key. One command per machine ends it: `security set-key-partition-list -S apple-tool:,apple:,codesign: -s -t private -l "Glosso Self-Signed" ~/Library/Keychains/login.keychain-db` (a *key* partition list — a different mechanism from a password item's trusted-app list, which is why the API-key fixes never touched it). The app's own read has its own cause and its own fix: `SecItemAdd` binds the item's ACL to the creating binary, so a re-signed build re-prompts; `security add-generic-password … -A` (any application, no partition list) settles it for good, and `APIKeyStore.save` can't undo that because it updates an existing item with `SecItemUpdate`, which leaves the ACL alone. Neither prompt is the cloud key being read speculatively — `SettingsStore` reads it only from the `SecureField` that shows it. Releases auto-ship via `.github/workflows/release.yml` on **merge to `main`**: a cheap check job compares `MARKETING_VERSION` against published releases and only then runs the macOS build → sign from CI secrets → `gh release create` (which makes the `vX.Y.Z` tag). Bumping the version in a PR is the release trigger — no manual tagging; merges that don't bump it are no-ops. The same job `sed`-repoints the hardcoded `releases/download/vX.Y.Z/Glosso.zip` links in `docs/index.html` to the new tag and commits it, so those pinned-version links are intentional and auto-maintained — don't "fix" them by hand. That commit lands on `main` a few minutes after each release, so a direct push right after one is rejected non-fast-forward: fetch and rebase onto it, nothing is broken. The repo is public so the update check and asset download work unauthenticated — see `docs/DISTRIBUTION.md`.

Live "Cannot find type X" / "No such module 'Testing'" diagnostics in the editor before a build are **SourceKit noise** (single module, not yet indexed), not real errors — verify against an actual `scripts/build.sh`/`test.sh` run.

CI has no test job — `.github/workflows/claude-code-review.yml` reviews a PR only when it touches `Sources/`, `Tests/`, `TestsIntegration/` or `project.yml`, so a docs-only PR getting no review is correct, not a stuck check; a new push cancels the in-flight review (`concurrency`), so during `/babysit-pr` wait for the run that follows your last push.

The popup and the Settings window **are** screenshottable, via `screencapture -x shot.png` in Bash (needs `dangerouslyDisableSandbox`, plus a one-time Screen Recording grant for the Claude host — without it the call fails with `could not create image from display`), then `Read` on the file and `sips -c h w --cropOffset top left` to crop out the panel. The `computer-use` MCP is **not** the way: `request_access` cannot resolve `Glosso`/`com.mirek.glosso` at all (an `LSUIElement` agent isn't enumerated as an application) and its screenshots filter every non-allowlisted app at the compositor level, so the popup and even the menu-bar glyph are missing from the image while the panel is provably on screen. `osascript -e 'tell application "System Events" to tell process "Glosso" to …'` reads the panel's title, subrole and geometry (e.g. `Tłumaczenie · EN → PL`, `AXSystemDialog`) — enough to assert direction detection and window size without a picture, though the SwiftUI children aren't exposed. To trigger a capture headlessly: type into TextEdit, `cmd+a`, then two `cmd+c` in one `computer_batch` (the ~0.3s window tolerates back-to-back synthetic presses). Dark mode is checkable without touching the user's system appearance: launch with `open --env GLOSSO_FORCE_DARK=1 .build/dd/…/Glosso.app`, which pins `NSApp.appearance` to `.darkAqua` for that run only (`AppDelegate.applicationDidFinishLaunching`). Reduce Transparency and Increase Contrast have no such hook — those are system settings, so ask the user to toggle them. All of that is **on request only**: the user verifies native UI changes manually, so after one finish with `scripts/run.sh` and say what to look at — no `screencapture`, no computer-use, no synthetic keystrokes unless asked for them. The **`docs/` landing is web**, though, so it *is* verifiable headlessly: serve it (`python3 -m http.server`, needs `dangerouslyDisableSandbox`) and drive agent-browser (`set viewport W H`, `screenshot --full`).

Tests use the **Swift Testing** framework (`import Testing`, `@Test`, `@Suite`, `#expect`) — not XCTest. To run one suite or test, add `-only-testing`:

```bash
xcodebuild test -project Glosso.xcodeproj -scheme Glosso \
  -destination 'platform=macOS,arch=arm64' -derivedDataPath .build/dd \
  -only-testing:GlossoTests/AppCoordinatorTests
```

`scripts/test.sh` prints only a terse "done" — for pass/fail/skip counts run `xcrun xcresulttool get test-results summary --path .build/TestResults.xcresult`. To iterate on a `PromptBuilder` change against the real model without rebuilding the app, POST the built prompt straight to Ollama: `curl -s localhost:11434/api/generate -d '{"model":"gemma4:26b-mlx","prompt":"…","stream":false,"think":false,"options":{"temperature":0},"keep_alive":"30m"}' | jq -r .response` (needs `dangerouslyDisableSandbox`). Mirror the locked options so the output matches the app's.

## Architecture

**`Sources/Core/Contracts.swift` is the frozen seam.** Every module talks to the others only through the protocols and value types defined there (`LLMClient`, `HotkeyMonitor`, `PasteboardReading`, `AXSelectionReading`, `TranslationPopupPresenting`, `AccessibilityAuthorizing`, `DoubleKeyDetecting`, `ModelListing`, `EngineProviding`, `ModelManaging`, `LoginItemManaging`, `SelectionReplacing`, `ReaderPresenting`, plus the `TranslationEvent`/`TranslationError`/`CaptureError`/`SecondLanguage`/`Formality` enums, `Action`, `KeyChord` and `LLMConfig`). `PrimaryLanguage` and the bilingual UI-string helper `loc(pl, en)` live next door in `Sources/Core/L10n.swift` (PR #87): the primary (Polish or English) is the fixed side of the translation pair, and every `LLMClient` method takes it as `primary:`. The UI language is **decoupled** from that setting: `L10n.current` is seeded once from the macOS language (`Locale.preferredLanguages`, any non-Polish system → English) and fixed for the process lifetime (Mutex-backed so `Sendable` code can read it off the main actor; the `@TaskLocal` `L10n.override` pins it in parallel test suites — and in any test asserting on `loc()` strings, since the default now follows the machine's language). `LLMClient.run(_:action:model:primary:second:formality:style:)` and `prewarm(model:)` take the user-selected model, language pair and palette verb (`Action` — issue #23) per call; `style` is a `fixGrammar`-only modifier (moderate style pass, issue #73), applied automatically whenever the direction's `supportsStyleFix` allows. The `Action` **case order is load-bearing**: it drives both the popup's verb-pill order and the background prefetch priority. `alternatives(for:in:source:primary:second:model:)` (non-streaming, returns `[String]`) and `reword(original:to:in:source:primary:second:formality:model:)` (streaming, like `run`) back the per-word alternatives feature (issue #17); `explain(word:in:source:primary:second:model:)` backs the per-word "Dlaczego tak?" line (issue #39), `explainFix(error:correction:original:corrected:primary:second:englishRules:style:model:)` the grammar-diff fix reasons (issue #51), `explainRegister(previous:current:from:to:source:primary:second:model:)` names what the tone pill actually changed between two register renderings (issue #53), and `reply(to:model:)` returns several reply drafts for the `reply` verb (issue #60), which rides the same pipeline but takes this non-streaming list path, not `run()`. `translateBlock(html:into:model:)` (one article block → the primary language, inline tags preserved), its batched sibling `translateBlocks(_:into:model:)` (several blocks in one request, sent as `<seg id="N">` elements and keyed back by those ids — the reader's answer to a per-minute request cap) and `readerSummary(of:into:model:)` (the reader's 2–3 sentence tl;dr) serve the URL reader and translate **into the primary language** — an article's language is unconstrained, so neither takes `second:`; `askArticle(question:history:article:into:model:)` and `articleQuestions(about:into:model:)` back the reader's ask-the-article chat (PRs #89/#90). All of these reader calls are non-streaming with a 300s timeout (`OllamaClient.longFormTimeout`), while every interactive lookup keeps URLSession's 60s default. Concrete types are injected; tests swap in fakes from `Tests/Support/`. When changing a cross-module behavior, change the protocol here first.

`AppCoordinator` (`Sources/Coordinator/`, `@MainActor`) wires the modules and owns the flow. `AppDelegate` (`Sources/App/GlossoApp.swift`) builds the real instances and starts it; it **early-returns under XCTest** (`XCTestConfigurationFilePath`) so the app side effects don't fire during tests. The coordinator also owns the **action cache + prefetch** (issue #58/PR #77): finished results are cached per `Action` so switching verbs is instant, a single background `prefetchTask` pre-generates the other verbs in `Action.allCases` order — but **only under the local provider**, since the cloud meters every call and three guessed verbs per capture would spend 4× the daily budget (and, at Flash Lite's 15 RPM, park a foreground translate behind three speculative ones in the limiter's wait) — and the cache is dropped when its signature (model/primary/second snapshot) changes, on reword undo, and on popup dismiss (which also clears `lastCapture` so a per-word fetch can't resurrect a stale prefetch).

The functional modules, each behind a protocol:

- **Hotkey** (`Sources/Hotkey/`) — `GlobalHotkeyMonitor` is a *passive* `NSEvent.addGlobalMonitorForEvents(.keyDown)` watcher matching the **typed character** "c" + Command (not the physical keyCode 8, so it also fires on Dvorak/AZERTY/Colemak). Both Cmd+C presses still copy normally. `DoubleCopyDetector` decides "double" by measuring the gap (~0.3s window) and resets after a hit so a third rapid press can't pair with the second. This is why the only OS permission needed is **Accessibility**, not a registered hotkey. The same monitor also resolves two **configurable headless chords** (`ChordHit.fix`/`.translate`, issues #21/#46): "fix grammar in place" (default Ctrl+Cmd+G) and "translate in place" (default Ctrl+Cmd+T), read live from `SettingsStore` via `chordProvider` and matched by character (`resolveChord` is pure/testable), firing `onFixGrammarInPlace`/`onTranslateInPlace`.
- **Capture** (`Sources/Capture/`) — reads `NSPasteboard`. `SelectionGuard` enforces that `changeCount` rose above a baseline (proof the user actually copied) and that the text is non-empty. When the poll loop times out (the app never copied on Cmd+C — Safari/WebKit does this inconsistently), `AppCoordinator` falls back to `AXSelectionReader` (`AXSelectionReading`), which reads the focused element's `AXSelectedText` directly via the Accessibility API — no pasteboard, no new permission (the AX consent the hotkey monitor already needs covers it). Because that read resolves whatever is focused *at fallback time* (~480ms after the press), `AppCoordinator` snapshots the frontmost app's PID at the double-press and bails out of the AX fallback if it changed (a Cmd+Tab mid-poll), so it never translates another app's selection. Deeper fallbacks (AppleScript, synthesized Cmd+C, Safari-via-JavaScript) stay deferred.
- **LLM** (`Sources/LLM/`) — the prompt layer is engine-agnostic and lives **once**, in `PromptRunning.swift`: `extension LLMClient where Self: GenerationBackend` implements every prompt-shaped `LLMClient` method on top of three transport primitives (`generate`, `streamGeneration`, `prewarm`), so a new engine writes only those three. Two backends conform: `OllamaClient` and `GeminiClient` (Gemma on the Gemini API, `generateContent` / `streamGenerateContent?alt=sse`, key in the `x-goog-api-key` header, `GeminiSSEParser` mirroring `NDJSONStreamParser`) — but `OllamaClient` serves **two** of the three providers: passing it a `keyProvider` and `OllamaCloudCatalog.baseURL` turns it into the Ollama Cloud backend, since that host speaks the same `/api/generate` NDJSON with an `Authorization: Bearer` header (the direct-API model ids drop the `-cloud` suffix that the local-proxy route requires — `gemma4:31b`, not `gemma4:31b-cloud`). The key's presence is the discriminator for three behaviors: an empty key throws `.missingAPIKey` before any network work, `prewarm` returns immediately (nothing is resident to warm and it runs on every launch), and failures map to the cloud cases instead of `.ollamaUnreachable`/`.httpStatus` — **load-bearing**, because `RoutingLLMClient.fallsBack` accepts only the cloud cases, and the cloud's 401 body (`{"error":"Unauthorized"}`) decodes as a `GenerateChunk.error` that would otherwise mask the status behind a never-falling-back `.ollamaError`, which is why a cloud instance checks the status code first. There is deliberately **no rate limiter** on this path: Ollama meters GPU time in 5-hour and weekly windows, publishes no request-per-minute cap, and a 429 simply hands over to the local engine. `OllamaCloudCatalog` holds only a base URL and a default model id — the model *list* comes live from `/api/tags` on `ollama.com`, which answers unauthenticated, so a retired cloud model (Ollama publishes a retirement schedule) can't rot into a hardcoded catalog. The alternative access route needs no code at all: `ollama signin` plus `ollama pull gemma4:31b-cloud` puts a cloud model on `localhost:11434`, where the Settings "other installed models" picker already finds it. `generationConfig.thinkingConfig.thinkingLevel: "minimal"` is the cloud counterpart of `think:false` and is **equally mandatory**; `prewarm` is a deliberate no-op there because `AppCoordinator.start()` calls it on every launch and there is nothing resident to warm. `RoutingLLMClient` picks the backend per call from `SettingsStore.provider` (`cloudBackend` maps the provider to Gemini, Ollama Cloud, or nil for local) and falls back to the local engine on `quotaExhausted`/`rateLimited`/`missingAPIKey`/`invalidAPIKey`/`cloudUnreachable` — swapping in `settings.modelName`, since callers pass `settings.activeModel` and Ollama wouldn't know a cloud model id. A stream that already yielded a token never falls back (the popup is showing it). It also falls back when the cloud simply **says nothing** for `deadline` seconds (6 by default, injectable for tests): measured on the free tier, `gemini-3.5-flash-lite` needs ~30s for a 43-token prompt and delivers its whole SSE stream in one shot, so no error ever fires and the popup sits on its skeleton — the deadline reports it as `.cloudUnreachable` and the existing fallback path takes over. It covers the **first token only** (a live stream may pause as long as it likes) and, on `generate`, only calls that brought no `timeout` — the reader's long-form calls legitimately outrun it. It also stands down when `localReady` says no: the cloud is sold as the **no-download** path (`OnboardingView.cloudModelStep` never pulls a model), so on those installs a hand-over would replace a slow answer with none at all — `AppDelegate` answers it with `engine.status() != .needsDownload` — `.installable` counts, because the local path provisions on demand and the error-driven fallbacks already hand over on that same bar — deliberately **not** `activeBaseURL()`, which is the provisioning path: it spawns `ollama serve` and polls up to ~2min inside an uncancellable task, so it would outlast the very deadline it gates and hold a finished cloud answer in the task group. The probe is asked only when the deadline is about to fire, and must stay cancellable, since the group cannot return until it does. `GeminiRateLimiter` (actor) paces the free tier and **blocks rather than throws**, because `ReaderController.translate` aborts a whole article after two consecutive errors; only the daily quota throws. The limits come **per model** from `CloudModelCatalog.Entry.limits` (the numbers are from the API console, since Google's public rate-limit page lists no Gemma rows) and the model id is passed into `acquire`/`quotaUsage` rather than read from settings — the id must be the one the in-flight request was built with, not whatever the picker shows by the time the limiter runs. Both the minute window and the Pacific-day counter are keyed by model id: a shared window stalls a switched-to model for up to 60s on a minute it never spent (Flash Lite's legal 200k tokens fail Gemma's 16k check, and a non-empty window skips the oversized-prompt escape hatch), and a shared daily bucket would let Gemma's 14 400 close Flash Lite's 500. It reserves an estimate (`utf8.count / 4`) and reconciles it against `usageMetadata.promptTokenCount`; the `Ticket` carries its model so settling can't credit another model's window. The per-model UserDefaults keys replaced the old flat `gemini.requestsToday`, so upgrading zeroes the day's count once — harmless, Google's own 429 backstops it. Because it blocks silently, `acquire` also calls an `onWait` closure with the wait length just before sleeping; `AppDelegate` wires it to `ReaderController.cloudWait`, which is the only reason a throttled article says "waiting" instead of freezing its progress line. That hop goes through the concrete `ReaderController` `AppDelegate` already builds, deliberately **not** through `Contracts.swift` — a status string is not worth widening the seam. Gemma has no paid tier on this API, so the local fallback is the only escape from the limits. `OllamaClient` POSTs to `/api/generate` with `stream:true`, parses the NDJSON line stream (`NDJSONStreamParser`), and yields `.token`/`.finished` through an `AsyncThrowingStream`. `PromptBuilder.build(for:action:primary:second:formality:style:)` carries the **primary↔second swap logic inside the prompt itself** and branches per palette verb (`Action` — issue #23): `translate` (the default, with the always-on humanizer directive), `summarize`, `fixGrammar` (with the optional `style` pass) and `reply` (drafts list, parsed by `ReplyParser` — issue #60). Plus the per-word `buildAlternatives` (one-per-line list, parsed by `AlternativesParser`) and `buildReword` (constrained re-translation) prompts for issue #17. Fix reasons are **grounded in static rule bases** (issues #73/#76): `PolishSpellingRules` (RJP-derived spelling + style cards) and `EnglishGrammarRules` (typical Polish-speaker errors); `englishRules` picks the grounding from the detected *source* language of the correction run — detection can misfire on short/mixed text, so the flag is passed in from the run, not re-detected per tap — and the Polish style cards join the base only when the run had `style` on. `prewarm(model:)` is best-effort (failures are swallowed) and keeps the model resident via `keep_alive`. Any directive folded into the translate prompt must stay **subordinate to the translation and name the target language**: a humanizer phrased in English-style terms ("write as natural prose, avoid em dashes…") made Gemma rewrite an English source *in English* instead of translating it to Polish — verify both directions against live Ollama after any prompt-wording change.
- **Popup** (`Sources/Popup/`) — `TranslationPopupController` shows a borderless non-activating `FloatingPanel`. `present()` follows `orderFrontRegardless()` (a background agent's plain `orderFront` can be refused) with `makeKey()`, so the panel owns the keyboard from the moment it appears — without it the controls and the editable source field only worked after a first click. `.nonactivatingPanel` is what keeps the **app** from activating, so the frontmost app stays frontmost and keeps its selection; that, not the key status, is the "won't steal focus" part. Esc dismisses it (via the CGEventTap below) and the title-bar close button closes it; a click *outside* the window closes only an open alternatives dropdown (issue #30), never the panel — that outside-click-to-dismiss-the-panel was deliberately dropped in `5f4a549` once the window became movable with a close button. **The controller owns the window size** — the only stable arrangement found (the resizable-popup work): the hosting view runs with `sizingOptions = []` (no constraints at all), PopupView measures its own ideal size in SwiftUI (`.fixedSize()` + `.onGeometryChange` — fixedSize is load-bearing: under a concrete proposal the panes' ScrollViews greedily fill the window instead of reporting content size) and reports it to `applyContentSize()`, which — coalesced to the next runloop turn — sets the whole frame with the top-left pinned so the panel grows downward, not up over the cursor. Every alternative was tried and fails: `.preferredContentSize` resizes the window from inside window layout (`updateAnimatedWindowSize`) and recurses to a stack overflow under a live grip drag; `.intrinsicContentSize` installs real constraints and the window's autolayout repositions the window with a drifting origin; competing `setFrame` calls get reverted synchronously; pinning the SwiftUI root frame recurses layout. The text panes cap height at 400pt and scroll; their padding sits on the pane `VStack` **outside** the ScrollView, so the overlay scroller draws over the last letters of a line unless the scrolled content itself steps aside — `.padding(.trailing, PopupView.scrollerInset)` *inside* the ScrollView. `.contentMargins(.trailing, …, for: .scrollContent)` looks like the right API and is not: measured on screen it moved the indicator inward and left the text where it was. A negative trailing padding on the ScrollView (`scrollerOverhang = scrollerEdgeGap - padPane`) then lets it reach past the pane's own 15pt so the scroller sits 6pt from the card edge while the pane headers and the retranslate button stay put. The bottom-right grip (`ResizeGripArea`, an `NSView` — a SwiftUI `DragGesture` never receives the drag) stretches pane widths and that cap via `PopupModel.sizeDelta`, and the window follows the grown content through the same single path. **Window moving** is a `WindowDragGesture` + `.allowsWindowActivationEvents()` on the card (interactive children win arbitration; it cannot fire over the grip — events over an `NSViewRepresentable` never enter SwiftUI's gesture graph), with `isMovableByWindowBackground` permanently **false**: the background-drag region is published to the WindowServer ahead of time for the whole window, so with it enabled a grip drag also moved the window and nothing reactive (hover toggles, dynamic getters, dummy gestures) can stop it. The panel's shadow is **AppKit's** (`FloatingPanel.hasShadow`), not a SwiftUI one: a hand-drawn shadow has only the window's transparent margin to blur into, so a radius wide enough to look soft gets clipped by the window edge and reads as a hard line. AppKit renders it outside the frame instead. It also **caches** it — `applyContentSize()` calls `invalidateShadow()` after the frame settles (once, at the end of the animation, not per step), or the shadow keeps the silhouette it had before the dropdown grew the window. The dropdown carries no `.shadow()` of its own either — it is a window now, so AppKit gives it the same treatment, and a blur on top of that is what drew the ring that once justified turning `hasShadow` off in the first place. The window reserves a transparent `PopupView.shadowMargin` around the visible panel for the blur, and `present()` shifts the window top-left up-left by that margin to keep the panel under the cursor — any positioning change must account for it. In the `.done` phase the result becomes a `FlowLayout` of individually clickable words (`WordFlow.swift`: `Tokenizer`, `FlowLayout`, `AlternativesDropdown`); clicking one opens an alternatives dropdown that lives in its **own child window** (`TranslationPopupController.dropdownPanel`, a second `FloatingPanel` added with `addChildWindow(_:ordered: .above)` so it rides along with the parent and closes with it). It used to be an in-window SwiftUI overlay, and the reason it moved is the panel's AppKit shadow: an overlay anchored to a word straddles the card's bottom edge and so sits in two shadow regimes at once — over the card the window shadow reaches nothing and the popover looks flat, past the card every blur of its own lands *on* the window shadow and draws a hard ring. No radius satisfies both; a separate window has no edge to cross. `PopupView` keeps only the anchor plumbing: `backgroundPreferenceValue(WordAnchorKey.self)` resolves the clicked word's rect, offsets it by `proxy.frame(in: .global).origin` and hands it up through `reportDropdownAnchor`; the controller converts that to screen coordinates (SwiftUI's y grows downward, so screen y is `parent.frame.maxY - anchor.maxY`) and clamps with the same `PanelPositioning.clampedTopLeft` the panel uses. It stays a plain window rather than an `NSPopover`/`Menu`, which would take key status from the panel. Esc is layered: it closes an open dropdown first, then dismisses the panel. This trades away drag-to-select on the result (the header Copy button still copies the whole translation). The source pane is an editable `TextField` (`sourceText`, issue #44) — edits plus an explicit re-translate re-run over the changed text. In the `fixGrammar` action the `.done` phase renders a **grammar diff** (`GrammarDiff.swift`) instead of the word flow: changed spans are tappable and open the dropdown straight into a one-line "why" reason in the UI language (`fixReasonMode`, issue #51), which is why Esc layering special-cases it (no list to peel back to). A dense diff (>3 changes, `PopupModel.splitFixView`) splits the pane into a diff section plus a clean corrected-text section with an eye toggle that hides the diff (PR #79) — `diffHidden` is deliberately transient (reset on every fresh capture) so the learning layer can't stay silently off, and hiding closes any open reason dropdown since its anchor vanishes. The `reply` verb renders its drafts as a radio list (`Picker(.radioGroup)`, issue #60). Materials go **the way a Notes window does it**: the card is an opaque surface (`textBackgroundColor`) and the glass belongs to the things floating over it — the header icon buttons, the retranslate button and the alternatives dropdown. The controls speak the **reader toolbar's vocabulary**, deliberately, so the app's two windows don't read as two designs: mutually exclusive choices are one segmented capsule with a filled segment (the verbs and the tone, matching the reader's language sides), and actions are separate circles with room between them (`.buttonStyle(.glass)` + `.buttonBorderShape(.circle)`, matching its `NSToolbarItem`s). Both follow HIG's "Buttons": enough space around a button to tell it apart from its neighbours, and no more than one or two prominent buttons per view — which is why the active verb is a plain filled segment and not an accent-coloured one. That dropdown carries **no backdrop of its own**, deliberately: anchored to the clicked word it straddles the card's bottom edge, so its upper part samples the card's white and its lower part the desktop. That is what a real macOS menu extending past its window does, and an opaque fill behind the glass only trades it for a flat white box — the position is worth more than a uniform material. The card draws its own 0.5pt hairline even with the window shadow on, since over a white app the shadow alone leaves the top edge without a contour. Two findings from the screen, neither in Apple's docs: the panel takes key on open but the **app never activates**, and the active appearance follows the app, not the key window — so without `.environment(\.appearsActive, true)` on the view root every control renders in the window-inactive appearance — gray labels, and a segmented control whose selected segment is indistinguishable from the rest, which is exactly what the verb and tone pickers depend on; and `GlassEffectContainer` **merges neighbouring capsules into one shape and one appearance**, so nothing here uses it — a merged cluster costs each button its own hit region and any per-button state. `Glass.tint(.accentColor)` is also worth knowing about: it draws nothing visible on a light panel, so a tinted glass button is not a way to mark selection. `PopupTheme` is now geometry, type and nothing else; the indigo brand colour lives only on the landing page. Word and diff highlights inset their fill outward (`.padding(.horizontal, -2)` on the shape) rather than padding the text, which is what used to render a double space between words and a gap before punctuation.

A **Reader** module (`Sources/Reader/`) turns a copied article URL into a translated reader window (double Cmd+C over a bare URL). `URLDetector.articleURL(in:)` gates it: only the *whole* trimmed selection being one http(s) URL with a host qualifies, and only the two **provably-fresh** capture sites route through `AppCoordinator.route()` — the trailing-changeCount retry deliberately streams to the popup instead, because its baseline is seconds old and a stale URL must never yank focus into a reader window. `ArticleExtractor` fetches the page in a hidden `WKWebView` and runs the vendored Mozilla **Readability.js** (`Vendor/`, bundled via `project.yml`'s `buildPhase: resources` — XcodeGen would otherwise try to *compile* the `.js`), with three pre-passes the extract needs on real pages: dropping CSS-hidden text (`checkVisibility` on the **live** document — a clone has no computed styles; image-bearing subtrees are exempt), promoting `data-src`/`data-srcset` lazy-loader attributes, and rescuing image-dominated `<aside>` galleries that Readability would strip. The last two also carry **embedded video**, which needs both halves to survive: a consent-gated YouTube player ships as an `<iframe>` with only `data-src` (our hidden webview never consents, so the src is never set), sitting inside an `<aside>` that `_clean(articleContent, "aside")` deletes unconditionally. So the promotion sets `src` on iframes too and the aside rescue accepts an embed instead of an image — both gated on Readability's own `REGEXPS.videos`, so a lazily-loaded ad iframe is never revived and no ad box rides the rescue into the article. The promoted URL is rewritten to `youtube-nocookie.com`, and the promotion runs on the *clone*, which is never rendered — the extractor itself makes no request to YouTube. `NavigationWatcher` bridges one navigation into async/await and **matches the `WKNavigation` identity**, so a superseded load in the shared webview can't fail its successor. `ReaderController` (`ReaderPresenting`) owns one window (a normal titled `NSWindow`, unlike the popup's panel), releases it and its WebContent process on close, and drives the pipeline: template load → extract → then the **title and tl;dr run concurrently with the block translation**, not ahead of it (`async let heading`). They were the larger half of the wait before the first paragraph appeared — measured, that head phase costs 1.5s on Flash Lite but 10.3s on Google's Gemma and 47.7s on Ollama Cloud, where a 91-token summary alone took 41.7s. They paint into their own slots (`glossoSetTitle`/`glossoSetSummary`), so nothing downstream needs them. Two things make the overlap safe: the 6000-char summary input is **snapshotted before any block translates** (`headText`) — it used to scrape the live DOM, which concurrently would summarise a half-translated article — and neither head call writes the status line any more, since the block counter owns it. The pipeline cancels the previous run on a new `show()` and gating every status write on `Task.isCancelled` so a dead task can't paint over the live one. Blocks whose text `NLLanguageRecognizer` reads as confidently already in the primary language (≥0.8, ≥40 chars, **unconstrained** recognition so e.g. Slavic kin can't pass as Polish) skip the model entirely. `translateBlock` caps generation at `max(256, html.utf8.count)` tokens per block — a flat `num_predict` ceiling falsely truncated markup-heavy blocks (PR #88). `ReaderTemplate` holds the page as a Swift constant plus the JS contract (`glossoSetArticle`/`glossoApply`/`glossoSetTitle`/`glossoSetSummary`/`glossoAbort`/`glossoSetMode`/`glossoSetChat`/`glossoSuggesting`, plus the chat's `glossoSetQuestions`/`glossoAnswer`), reached only through `ReaderTemplate.call`, which JSON-encodes every argument. Status and engine share the **window's subtitle** (`refreshSubtitle`), where the page used to draw a two-slot footer bar: the block counter while translating, then "provider · model id" (`ReaderController.engineLabel`, set from `insertArticle` so the cached replay gets it too). A cached article replays the label **stored in `ReaderCache.Entry.engine`**, not the current setting — the point of the line is who translated *this* text, and a replay inside the 7-day TTL can easily outlive a provider switch; the field is optional, so entries written before it existed fall back to the engine in use now. Its right edge shifts by the chat panel's width like the pills do, or the panel would cover the label; the status slot carries `min-width: 0` and an ellipsis, or its longest word wins the row and pushes the label out of the bar; visibility follows **either** slot, since the bar now outlives the status text. When `RoutingLLMClient` hands a running article to the local engine, `AppDelegate`'s `onFallback` calls `engineFallback()` and the label repaints as local for the rest of that article. That hop is gated on **two** things, and both are load-bearing: `translating` (as `cloudWait` is), and `onFallback`'s `longForm` flag — the closure is shared with every popup capture, and since only the reader's calls carry a timeout, `longForm` is what tells them apart. Without it a popup lookup missing the 6s first-token deadline (routine on Flash Lite, ~30s to first token) would relabel an article the cloud is still translating, and nothing would set it back. Two invariants there are load-bearing: **`glossoSanitize` runs after every `innerHTML`** (Readability strips `<script>` but keeps `on*` handlers and `javascript:` URLs, and `innerHTML` fires `<img onerror>` on insert), and the original/translated views live side by side in JS (`glosso.original`/`translated`/`pending`), so switching sides is a DOM re-render, not a re-translation. The page wears the **"Dwugłos" bilingual-edition design** (ported in `a13a481` from `mockup/reader/dwuglos.html`, since removed with the rest of `mockup/` in `d7d4842`): Athelas/Palatino serif with Avenir Next UI, a centered book title page (fleuron ornament), the tl;dr as a rule-bounded "Od tłumacza" note, quotes as centered epigraphs, and and the **chat panel deliberately outside all of it** — it is a conversation, so it wears the UI font and Messages-style bubbles (accent for the question, `light-dark(#E9E9EB, #3A3A3C)` for the answer, capsule suggestion chips, a circular send button whose label lives in `aria-label`) rather than the numbered footnotes it started as — plus the **interlinear original**: clicking a translated block (tagged `.glosso-dual` at apply time; classList survives the innerHTML rewrites) inserts its stored original under it as an indented citation, cleared naturally by any view re-render. The walk registers each **direct `<li>` of a list as its own block** (the ol/li skeleton stays in the DOM so numbering survives whatever the model returns; nested lists stay inside their parent li's block — tagging them would let a parent apply wipe the children's ids). The window's chrome is a real **`NSToolbar`** (`Sources/Reader/ReaderToolbar.swift`, `toolbarStyle = .unified`): a refresh item, an `NSSegmentedControl` carrying the detected language codes (PL | EN, from `ReaderController.languageLabels`, falling back to Tłumaczenie|Oryginał), and a chat toggle. It gets Liquid Glass and the system's own behaviour for free, and it inverts the ownership of that state: **Swift holds the mode and the panel flag and the page only applies them** (`glossoSetMode`, `glossoSetChat` are idempotent setters, not toggles), so a native control can never desync from the page. `ReaderController` is not an `NSObject`, so target/action goes through `ReaderToolbarProxy`, the same shape as `ReaderScriptMessageProxy` next door; the items sit after one leading `.flexibleSpace`, because a unified toolbar shares its row with the title and spreading them pushes the last item into the overflow menu. That leaves **`ask` as the only JS→Swift message**; refresh drops the cache entry and re-runs the full pipeline from Swift. The **ask-the-article chat** (PRs #89/#90) opens a fixed side panel; the window *widens* by `chatPanelWidth` (capped to the visible screen) instead of squeezing the article, and the pills stay over the article column (PR #93). First open lazily generates suggested-question chips (best-effort — a failure paints an empty list so the chip spinner resolves); answers go through `askArticle` carrying the last 4 exchanges of `chatHistory`. `suggestTask`/`askTask` are deliberately separate from `translationTask` — a chat query must never cancel the running translation, and superseded chat tasks guard on `Task.isCancelled` exactly like the pipeline. The chat context is read from the **currently displayed** text, so the chat sees whichever side the language segment shows. **Never trust the shape of a model's answer**: every model string that reaches the page goes through `ReaderTemplate.unwrap`, which peels a markdown fence *and* an echoed `<block>`/`<text>`/`<article>` wrapper, in either nesting order — Flash Lite answers `buildBlockTranslation` with the prompt's own wrapper, which `glossoSetTitle`'s `textContent` renders literally while `innerHTML` hides it and then persists it into the cache. The prompt's "without the wrapper" clause only lowers the rate; `unwrap` is the fix. Chat answers additionally go through `ReaderTemplate.markdown`, which renders the emphasis models emit whatever the prompt asks for (`**b**`, `*i*`, `` `code` ``, `-`/`#` line starts) — HTML-escaped **first**, so the only tags that reach `glossoAnswer`'s `innerHTML` are the ones we add; `chatHistory` keeps the raw answer, since that is context for the model, not for the DOM. Blocks per request come from `ReaderController.batchSize(provider:model:)` — an extracted policy like `countsTowardAbort`, keyed **per model** because a live sweep showed the two Gemini models are bound by opposite things. Local 1, Ollama Cloud 5 (`OllamaCloudCatalog.batch`, one number for all 19 models there), and per-entry `CloudModelCatalog.Entry.batch`: Flash Lite 20, both Gemmas 10. The numbers are measured, not reasoned: swept live against the real reader corpus (median block 139 B, mean 192 B, p90 362 B, max 1249 B, pulled from `~/Library/Caches/Glosso/reader`), **nothing broke the `<seg id>` round trip anywhere in range** — Gemma stayed clean to 40, Flash Lite to 80, local to 20 — so these are latency and blast-radius choices, not correctness cliffs. Flash Lite gets the big one because its cost is nearly fixed per call (11.9s at 5 blocks, 24.3s at 80) and its scarce resource is the **500-request day**, which one long article eats 16% of at 5 blocks; Gemma gets half that because its cost is nearly *linear* (16.6s at 5, 68.3s at 20), so a bigger batch is mostly a longer stall before the first block paints. Flash Lite's only observed failure, at 80+, was `finishReason MAX_TOKENS` — and that is **not** silent: `GeminiClient` throws `.malformedStream` on it, as `OllamaClient` does on `done_reason == "length"`. Local stays at 1 because measured per-block wall clock is flat there (2.95s at one block, 2.28s at ten, 2.87s at twenty) — the best point sits inside the sweep's own noise band. Ollama Cloud stays at 5 because the sweep **refuted** the reason to raise it: that host bills GPU *time*, and wall clock is flat at ~2s per block from 5 to 40, so a bigger batch buys ~nothing in the metered currency (prompt tokens per block do fall ~42%, but they are evidently a small share of the bill). `ReaderTemplate.batches` packs greedily under both that count and a 4000-byte budget, which at the corpus mean fits ~20 blocks — so it stops binding right where the largest batch size sits and quietly shrinks batches on above-average articles instead. The count is a **ceiling the packer ramps up to**, not a starting point: batches go 1, 2, 4, … up to it, so the first request carries a single block and something paints while the big batches are still being packed (on Gemma that is the first paragraph at ~7s instead of ~26s). The ramp is a geometric prefix, so it costs a fixed handful of extra requests **once per article** rather than a share of it — that is what makes it safe to apply to Flash Lite's 500-request day too — and at `maxCount` 1 it degenerates to the local engine's per-block behaviour for free, which is why no second per-engine knob exists for it. `BlockBatchParser` demands the exact **ordered** id list back, so a batch that throws or comes back reordered, short or empty is discarded whole and its blocks retry through the untouched per-block path: a failed batch therefore counts as **zero** failures against the two-failure abort, and one bad batch can never kill an article. Blocks already in the primary language are applied in a pre-pass so they never occupy a slot in a batch. `ReaderCache` persists a fully translated article to `~/Library/Caches/Glosso/reader` (one JSON per URL, SHA256 key, 7-day TTL, written only after a complete un-cancelled run); a hit replays the stored original through the same `insertArticle` path (deterministic block ids) and paints the cached title/summary/blocks with zero fetch and zero LLM.

Three smaller supporting modules: **Engine** (`Sources/Engine/`) — `EngineManager` (`EngineProviding`) finds or provisions the Ollama engine (`ensureEngine`, idempotent) via `OllamaEngineDownloader`, and `OllamaModelManager` (`ModelManaging`) pulls/deletes models through `/api/pull` (`PullProgressParser`). **Replace** (`Sources/Replace/`) — `SystemSelectionReplacer` (`SelectionReplacing`) pastes via a synthesized Cmd+V on `.cgAnnotatedSessionEventTap` with clipboard save/restore and a suppression filter — deliberately **not** AX-based replacement, which reports false success in web/Electron (issue #22). **Notify** (`Sources/Notify/`) — `SystemUserNotifier` posts user notifications for the headless in-place paths (success/failure/clipboard-fallback messages) and the new-version alert.

A **Settings** module (`Sources/Settings/`) holds the user-editable config: `SettingsStore` (`@Observable`, UserDefaults-backed) persists the `provider` (`LLMProvider.local`/`.cloud`/`.ollamaCloud`, local by default — either cloud sends the selection off the machine, so both are opt-in), the `cloudModel` (from `CloudModelCatalog`: `gemma-4-31b-it` default — Flash Lite is in the list but is not the default, since it answers in ~30s where Gemma takes ~1s — plus `gemini-3.5-flash-lite` and `gemma-4-26b-a4b-it` — the only two Gemma ids the Gemini API serves; each entry carries its own free-tier `limits`, and the default is resolved **by id, not by index**, so inserting a row can't silently re-point it; the `llm.cloudModel` key stays **absent** from UserDefaults until the user actually picks a model, since `didSet` doesn't fire during `init` — which is what lets a changed catalog default reach every install that never touched the list, without overriding an explicit choice) the `ollamaCloudModel` (same absent-until-picked rule, defaulting to `OllamaCloudCatalog.defaultModel`) and the computed `activeModel` that **every LLM call site reads** instead of `modelName`, since the three engines name models differently; the two `apiKey`s are *not* UserDefaults-backed but live in the Keychain via `APIKeyStore` (one service, two accounts — `google-api-key` and `ollama-api-key`, so picking a provider can't wipe the other's key), mirroring how `launchAtLogin` defers to `SMAppService`. It also persists the Ollama `model`, the `primaryLanguage` (PL/EN, PR #87 — the translation axis only; the UI language follows macOS via `L10n`, not this setting; installs predating the setting migrate to Polish), the `secondLanguage` (now `SecondLanguage?` — `nil` is the **automatic** mode, stored as an `"auto"` sentinel and resolved per capture by `DirectionDetector`; a second equal to the primary is auto-corrected to its counterpart), the popup tone (`formality`), `lastNotifiedVersion` for the update alert, and the two headless chords (`fixChord`/`translateInPlaceChord`, `KeyChord` JSON-encoded; defaults in `Contracts.swift`), the latter edited via the click-to-record `KeyChordRecorder`. `SettingsView` is a SwiftUI `Settings` scene (opened from the menu via `@Environment(\.openSettings)`) built as a `Form` with `.formStyle(.grouped)` — no custom title bar, no `containerBackground`, no hand-drawn cards, so the window keeps the system's Liquid Glass titlebar and scrolls itself. The scene sets `.defaultSize` and `.windowResizability(.contentMinSize)`: the user can grow it freely, it just can't shrink below the form. **Nothing in it scrolls** — `SettingsWindowConfigurator` sizes the window to the content on every change, since the form's height swings ~80pt between engines (measured: local 667.5pt, Ollama Cloud 707.5pt, Google AI 745pt) and a single fixed height either clips the last section or leaves a hole. Three findings there, none of them guessable: the grouped `Form` is scroll-backed, so SwiftUI reports the *window's* height back to you and the only honest number is the scroll view's `documentView.frame.height` (`SettingsWindowSizing.formContentHeight`, which the layout test also calls); `window.frameRect(forContentRect:)` reports **no title bar** on this window and cuts the last row off, so the chrome is measured as `frame.height - contentLayoutRect.height` instead; and the fit has to be coalesced to the next runloop turn, out of the layout pass, exactly as `applyContentSize` is in the popup. `updateNSView` fires on every body re-eval — including the 5s quota poll — so the fit no-ops unless the measured content height actually moved, which is also what lets a hand-dragged window survive until the next engine switch. The width is never touched: it drives the privacy note's wrapping, so it is the one dimension carrying user intent. Two content trims keep even the tallest engine under a 13-inch screen: the cloud model picker is a plain menu (a `.radioGroup` rendered all three models inline), and `ModelCatalogList` sits in a `DisclosureGroup` collapsed under either cloud engine, where it is the fallback rather than the daily choice. **Selection and management are split**: one "Aktywny model" `Picker` lists what is installed (the current pick is always in the list, even when it isn't downloaded yet), and `ModelCatalogList` — shared with onboarding — renders one row per `EmbeddedModelCatalog` tier with the gauge icon, the id/size/"zalecany" subtitle and a Pobierz/Usuń button or a progress bar. Those rows are an `HStack`, deliberately **not** `LabeledContent`: that container hands the row's label to its controls as their accessibility name, so every button would read out as the model's name instead of the action. One `NSViewRepresentable` survives, and only for two things the scene can't say itself: `.moveToActiveSpace` (an `LSUIElement` app's Settings window has to follow the active Space) and the window title, which SwiftUI composes from the unlocalized bundle even on a Polish system. `OllamaModelLister` (`ModelListing`, `GET /api/tags`, derived from the generate endpoint's host) still supplies the live installed-model list, and a second instance pointed at `OllamaCloudCatalog.baseURL` supplies the Ollama Cloud list the same way. Under either cloud provider the local radio list stays on screen relabeled as the fallback model, because both hand over to it on a dead key or a spent quota. There is no longer an engine row — a model download (`startPull`) provisions the engine lazily by calling `ensureEngine` (idempotent — a no-op when an engine is reachable) first. A "Launch at login" toggle binds to `SettingsStore.launchAtLogin`, which is **not** UserDefaults-backed: it derives from and drives `SMAppService.mainApp` through `LoginItemManaging` (`SMAppServiceLoginItem`), so the actual system registration is the source of truth (a user revoking it in System Settings is reflected on `refreshLaunchAtLogin`, called when the window appears). The empirical invariants (`think:false`, `temperature:0`, `keep_alive`, `endpoint`) stay locked in `OllamaClient`'s base config and are **not** exposed in the UI.

A first-run **wizard** (`OnboardingView`/`OnboardingController`, gated by `SettingsStore.hasCompletedOnboarding`) walks the user through model download → second language → usage + the one-time Accessibility grant; its model-pull flow is shared with Settings via `downloadModel()` (`ModelDownload.swift`). ### Three subtleties that aren't obvious from a single file

1. **The capture poll loop** (`AppCoordinator.captureAndTranslate`): the second Cmd+C only *triggers* the copy, so at the instant the double-press is detected the new clipboard contents aren't there yet. The monitor samples the baseline `changeCount` at the *first* Cmd+C (`registerPress`) — so it precedes the second copy even for apps that copy synchronously on keyDown (Chromium/Electron, Java) — and hands it to the coordinator via `onDoubleCopy`, which polls `readSelection` until `changeCount` rises (default 12ms × 40 attempts ≈ 480ms, to tolerate slow apps' copies) before streaming.

2. **`DirectionDetector` decides the translation direction.** `detect(_:primary:second:)` uses `NLLanguageRecognizer` (constrained to the primary + the second language) to pick both the arrow label (PL→XX / XX→PL) **and** the target language named in the translate prompt: `PromptBuilder.instruction(for:primary:second:formality:)` emits an unconditional "Translate … into X." Under the automatic second (`nil` in `SettingsStore`) the same detection also resolves which concrete second language the capture uses, and the direction carries it. Detection below a 0.8 confidence floor returns `.unknown` — short PL/EN homographs ("To", "Do") misdetect at ≤0.75 and, with the target now code-chosen, would translate English into English; correct reads measure ≥0.84. The earlier conditional swap in the prompt ("If it is Polish → X; otherwise → Polish") is kept only as the `.unknown` fallback — asking Gemma (`think:false`) to classify *and* translate in one step failed for non-English pairs (NL/RU sources came back echoed or lightly paraphrased instead of translated to Polish; verified live both with and without the humanizer).

3. **The headless in-place path** (`AppCoordinator.fixGrammarInPlace`, issues #46/#21): unlike double-Cmd+C, the chord triggers no copy, so it reads the selection straight from the focused element's `AXSelectedText` (falling back to a synthesized Cmd+C with clipboard save/restore when AX reads empty, e.g. web/Electron), runs `fixGrammar` or `translate` silently into a buffer, and pastes the result back — no popup. That fallback must not demand a *fresh* copy: a terminal with copy-on-selection (VS Code's default, `terminal.integrated.copyOnSelection`) already put the text on the clipboard when the mouse selected it, so the synthetic Cmd+C rewrites identical content — a no-op that never bumps `changeCount`, and the strict baseline can never rise. It therefore retries against `trailingChangeCounts` exactly like `captureAndTranslate`. Verified live: the synthetic Cmd+C itself is fine (it copies in the VS Code editor and in a plain-shell terminal); with a TUI running, no keystroke trick helps because there is nothing new to copy. Like `handleReplace`, it snapshots the source app's PID up front and bails (handing the result to the clipboard instead) if focus moved, so it never pastes into the wrong app.

## Tests

- `Tests/` — fast unit tests, no network, using the fakes in `Tests/Support/`. One of them measures real AppKit layout rather than pure functions: `PopupLayoutTests` renders `PopupView` and `AlternativesDropdown` in an `NSHostingView` and asserts each reports a non-zero ideal size that doesn't change on a second pass. Both windows size themselves from that measurement, so an unstable one feeds `setFrame` a new rectangle every runloop turn and a zero one opens an invisible window — and nothing else in the suite would notice either. It used to also check the dropdown's height against a hand-written reservation; that reservation died with the in-window overlay, since a window measures itself.
- `TestsIntegration/` — three live suites that all **silently skip (return early) when their backend isn't reachable**, so the suite stays green without a daemon or a key: `OllamaLiveTests` (`localhost:11434`), `OllamaCloudLiveTests` and `GeminiLiveTests` (skip without an API key in the Keychain).
- `Tests/Support/MockURLProtocol.swift` stubs `URLSession` — that's how `OllamaClient`/`GeminiClient`/`UpdateChecker` are tested without network.
- Every test/helper file needs `@testable import Glosso` to see our types, and `import Foundation` when it uses Foundation types (e.g. `TimeInterval`). Helpers under `Tests/Support/` are easy to forget.
