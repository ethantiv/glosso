# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Glosso is a macOS 26+ menu-bar agent (`LSUIElement`, no Dock icon, Swift 6 strict concurrency). On **double Cmd+C** it translates or grammar-fixes the selection with an LLM and streams the result into a floating panel near the cursor; a copied bare URL opens a translated reader window instead. `README.md` is the user-facing feature description; `docs/DISTRIBUTION.md` owns signing and release details.

Two load-bearing LLM decisions (guarded by `Tests/SanityTests.swift`): `think: false` is mandatory (Gemma otherwise spends 10–26 s on reasoning tokens for the same translation), and the app uses Ollama's native `/api/generate`, not the OpenAI-compatible `/v1` layer, which doesn't expose `keep_alive`.

## Commands

The Xcode project is generated by XcodeGen and git-ignored. Edit `project.yml`, never `Glosso.xcodeproj`. Every script regenerates the project first, so new source files are picked up automatically.

```bash
scripts/build.sh                 # Debug build → .build/dd/Build/Products/Debug/Glosso.app
scripts/run.sh                   # build, kill the previous Debug instance, launch
scripts/test.sh                  # offline tests → unique .build/TestResults-*.xcresult
scripts/test.sh --adhoc          # same, ad hoc signing (no "Glosso Self-Signed" cert needed)
scripts/test.sh --live local     # live suites; also: google (GEMINI_API_KEY), ollama-cloud (OLLAMA_API_KEY)
scripts/package.sh               # Release zip → .build/release/Glosso.zip; outside CI also installs into /Applications
```

Run a single suite or test:

```bash
xcodegen generate && xcodebuild test -project Glosso.xcodeproj -scheme Glosso \
  -destination 'platform=macOS,arch=arm64' -derivedDataPath .build/dd \
  -only-testing:GlossoTests/AppCoordinatorTests
```

Pass/fail counts: `xcrun xcresulttool get test-results summary --path <result.xcresult>`.

To iterate on a `PromptBuilder` prompt without rebuilding, post it straight to Ollama with the app's fixed options: `curl -s localhost:11434/api/generate -d '{"model":"gemma4:26b-mlx","prompt":"…","stream":false,"think":false,"options":{"temperature":0}}' | jq -r .response`.

Environment notes:
- `xcodebuild`, `gh` and network calls fail inside the Claude Code sandbox (`Operation not permitted`, or TLS `OSStatus -26276`). Run them with `dangerouslyDisableSandbox: true`.
- Editor diagnostics such as "Cannot find type X" or "No such module 'Testing'" before a build are SourceKit noise. Trust an actual `scripts/build.sh` or `scripts/test.sh` run.
- A Keychain password prompt during `scripts/run.sh` comes from `codesign` reading the signing key, not from the app.

## Workflow conventions

- The user verifies native Glosso UI manually. Don't drive the app with Computer Use, capture its windows or synthesize UI gestures. Rely on offline tests and tell the user what to check by hand. The `docs/` landing page can be checked in a browser.
- Put larger changes on a feature branch, not directly on `main`.
- User-facing changes bump `MARKETING_VERSION` in `project.yml`: minor for features, patch for fixes. Merging a new version into `main` *is* the release: `.github/workflows/release.yml` builds, signs and publishes it, then a bot commit updates the download links in `docs/index.html` and `docs/en/index.html`.
- Commit messages use `feat:`, `fix:`, `test:`, `refactor:`, `docs:` and `chore:` prefixes.
- Keep the signing identity (`Glosso Self-Signed`, manual style, no team). macOS pins the Accessibility (TCC) grant to it, so changing it forces every user to re-grant. Hardened runtime and the debug dylib are disabled in Debug only because library validation otherwise rejects the self-signed test bundle.

## Architecture

**`Sources/Core/Contracts.swift` is the seam.** Modules talk to each other only through the protocols and value types defined there (`LLMClient`, `GenerationBackend`, `HotkeyMonitor`, `PasteboardReading`, `AXSelectionReading`, `TranslationPopupPresenting`, `SelectionReplacing`, `EngineProviding`, `ReaderPresenting` and others). Tests substitute fakes at exactly these boundaries.

**Composition.** `AppDelegate` (`Sources/App/GlossoApp.swift`) builds the real instances and returns early under XCTest (`XCTestConfigurationFilePath`), so tests never trigger app side effects. It creates two `AppCoordinator`s that share one `RoutingLLMClient`: one driven by the global hotkey monitor, and one behind the Translator… window.

**Capture flow** (`Sources/Coordinator/AppCoordinator.swift`):
1. `GlobalHotkeyMonitor` passively watches keyDown for the typed character "c" + Command (layout-independent), so the only permission needed is Accessibility. It samples the pasteboard `changeCount` at the *first* press as the baseline. The same monitor resolves the two configurable in-place chords.
2. `captureAndTranslate` polls the pasteboard until `changeCount` rises above the baseline, because the second Cmd+C only triggers the copy. On timeout it falls back to `AXSelectionReader`, but only if the frontmost app's PID still matches the one at the press. As a last resort it retries against `trailingChangeCounts`, pasteboard snapshots taken every 2 s. This covers apps like VS Code, where key events arrive after the copy, so the baseline already reflects it. That retry always streams to the popup and never opens the reader, because its baseline can be seconds old.
3. `route()` sends a bare article URL to the reader (`URLDetector`) and everything else to the popup.
4. In-place chords (`fixGrammarInPlace`) read the selection through AX (falling back to a synthesized Cmd+C), run silently and paste back through `SystemSelectionReplacer`: a synthesized Cmd+V with clipboard save and restore. Pasting is deliberately not AX-based, because AX replacement reports false success in web and Electron apps.
5. Results are cached per `Action`. A background prefetch of the other action runs **only for the local provider**, because cloud calls spend a metered daily quota.

**LLM layer** (`Sources/LLM/`):
- The prompt layer exists once, in `PromptRunning.swift`: `extension LLMClient where Self: GenerationBackend` implements every `LLMClient` method on top of three transport primitives (`generate`, `streamGeneration`, `prewarm`). A new engine implements only those three.
- `OllamaClient` serves two providers. Without a `keyProvider` it is the local engine. With a `keyProvider` and `OllamaCloudCatalog.baseURL` it is Ollama Cloud: it signs requests and maps failures to the cloud error cases. `GeminiClient` serves Google AI behind the client-side `GeminiRateLimiter`, which blocks rather than fails.
- `RoutingLLMClient` picks the backend per call from `SettingsStore.provider`. It falls back to local on the errors listed in `RoutingLLMClient.fallsBack` and when a cloud stream stays silent past a deadline (6 s). Cloud errors must map to those cases, or the fallback silently stops working.
- Call sites pass `SettingsStore.activeModel`, never `modelName`, because the three engines name models differently.
- `DirectionDetector` (`NLLanguageRecognizer`, constrained to the configured pair) chooses the translation direction in code, with a 0.8 confidence floor. Below the floor it returns `.unknown`, and the prompt falls back to letting the model decide.
- `PolishSpellingRules` and `EnglishGrammarRules` ground the explanations for grammar fixes.

**Reader** (`Sources/Reader/`): `ArticleExtractor` loads the page in a hidden `WKWebView` and runs the vendored Readability.js. `ReaderController` translates in blocks (batched for the cloud), adds a summary and a side chat. Security boundaries live in `ReaderWebSecurity`:
- Page scripts run in an isolated `WKContentWorld`, and markup is sanitized with DOMPurify plus `ReaderSanitizer.js`.
- Script messages are accepted only from the main frame with the matching session id and an exact key set.
- Iframes are limited to an allowlist of video hosts.

Storage goes through the `ReaderRepository` actor: `ReaderCache` (Caches directory, 1-week TTL, key includes the app version) and `SavedArticleStore` (Application Support, user-chosen retention, pinned entries kept). `ReaderRunContext` freezes provider, model and language at the start of a run, so a Settings change mid-run can't mix outputs.

**Supporting modules**:
- `Engine/` finds or downloads the Ollama binary and pulls models.
- `Settings/` contains `SettingsStore`, which is `@Observable` and UserDefaults-backed. API keys are stored in the Keychain through `APIKeyStore`, one account per provider. The module also holds onboarding.
- `Update/` checks GitHub `releases/latest`.
- `Notify/` posts user notifications.

**Bundled JS**: any `.js` file must be listed in `project.yml` with `buildPhase: resources`, because XcodeGen otherwise tries to compile it. `Vendor/` holds Readability.js and DOMPurify.

**Localization**: UI strings go through `loc("polski", "English")` (`Sources/Core/L10n.swift`). The UI language follows macOS and is fixed per process. It is independent of `PrimaryLanguage`, the user's translation axis.

## Tests

- Swift Testing (`import Testing`, `@Suite`, `@Test`, `#expect`), not XCTest. Files need `@testable import Glosso`. Name suites `<Feature>Tests`.
- `Tests/` is offline and deterministic. Use the fakes in `Tests/Support/`: `CoordinatorFakes` for the protocol seams, `MockURLProtocol` to stub `URLSession` for the HTTP clients, and `ManualTestClock` for time. Default tests never touch the network or the Keychain.
- Tests that assert on `loc()` output must pin the language with `L10n.$override.withValue(.polish) { … }`, because the default follows the machine's language.
- `TestsIntegration/` is a separate `GlossoLiveTests` target and `GlossoLive` scheme. It runs only through `scripts/test.sh --live …`, and missing keys or services fail the run.
